## 1. すでにコードにあるもの（基準に依らない強制）

| 仕組み | 場所 | 内容 |
|---|---|---|
| LIVE ゲート | `packages/common/live_gate.py`, `scripts/live_gate.py` | 名前付きの人間の承認ファイルが有効（未失効）でなければ LIVE の**新規建て**は送られない。承認は期限付き（最大14日）で、承認できる最大エクスポージャ段階（0,1]を明記する。ファイル無し・破損・失効・範囲外はすべて閉。出口・保護ストップは止めない |
| 環境の紐付け | `BrokerAdapter.environment`, `ExecutionEngine.__post_init__` | アダプタが自身の接続先環境を申告し、エンジンの環境と食い違えば構築時に拒否（シミュレータをLIVEとして、またLIVE先をPAPERとして繋げない）。LIVE のエンジンはゲート無しでは構築不能 |
| 段階ガード | `ExecutionEngine.entries_blocked_by_live_gate` | 設定の `exposure_cap_stage` が承認された段階を超えていれば新規建てを拒否 |
| 監査の必須化 | `services/decision/audit.py` | LIVE では全注文が監査対象。監査不能・出力不正は取引ブロック（フェイルクローズ） |
| 緊急停止 | `scripts/kill_switch.py` | 新規建てを即停止（自動再開なし） |
| 資本ランプ | `RiskConfig.exposure_cap_stage` | 総エクスポージャ上限に乗じる段階値（§104） |

## 2. LIVE の前に解決が必要な技術的課題（実ブローカー接続の調査で判明）

| # | 課題 | 内容 |
|---|---|---|
| T1 | **保護ストップの有効期間** | **解決（2026-11-08）**: `TimeInForce`（DAY/GTC）を `OrderIntent` に追加し、注文の同一性（リスク承認の署名・スナップショットのハッシュ・スナップショット照合・ブローカー要求）に含めた。**STOP は GTC でなければ intent もブローカー要求も構築できない**（DAY の保護ストップは型として存在不能）。パイプラインの保護ストップは GTC。模擬ブローカーは DAY の休止注文をセッション翌日に失効させる（GTC は残る）。DAY 注文のハッシュ文字列は従来と同一（STOP のみ変化）。実ブローカーでは GTC の失効日（多くは期限あり）に別途注意 |
| T2 | 約定の取得範囲 | **解決（2026-11-07）**: 実行経路は注文単位の `get_order_fills(client_order_id)` を使い、全履歴の走査をやめた。`get_fills(since)` はインターフェースに残る（呼び出し側は範囲を限る） |
| T3 | PaperBroker専用の呼び出し | **解決（`poll_resting_orders`）**: 基底の既定は空（実ブローカーは自分で監視する）。休止中の約定は状態確認（`get_order_status`＋`get_order_fills`）で発見し、各約定は一度だけ台帳へ渡る（`sync_open_orders`）。以前は、自己監視するブローカーではストップ約定が台帳に入らず照合で全停止になる穴があった。`settle()` は模擬専用のまま（スクリプト／リプレイのみが呼ぶ。実ブローカーは自力で決済する） |
| T4 | アカウント状態 | **一部解決**: `get_account_status()`（取引停止の有無）を追加し、照合が「取引停止」を不一致として新規建てを停止する。買付余力・受渡日の取得は、実ブローカーの応答形式が分かってから（現金は `get_cash()` の既存項目） |
| T5 | 手数料の確定遅延 | **未着手（意図的）**: 後から確定する手数料の補正方式は、ブローカーの実際の挙動（Alpaca は株式の手数料が無料で規制費用のみ、IBKR はコミッション報告が後着）が分かってから設計する。当面、現金の照合（許容 0.05）が差分を検出して新規建てを止める＝安全側に倒れる |
| T6 | 取引カレンダー | **一部解決（2026-11-08）**: 2027・2028年の公式データを追加（出典・検証は `docs/MASTER_SPEC.md`）。2029年以降は未整備で拒否＝停止。ブローカー供給への差し替えと臨時休場の扱いは実ブローカー接続時 |
| T7 | 常時稼働の実行基盤 | **大部分が解決（2026-11-10）**: 実行器（ハートビート・失敗時の停止・障害ログと人による解決）、外部の監視役（`watchdog.py`、死活監視サービスへの ping）、通知の実送信（Webhook／メール／履歴）、運用ダッシュボード、運用手順書、**ペーパー口座の永続化（保存・検証つき復元・自動再起動。`services/checkpoint.py`）**。**残り**: 通知先への実送信の実地確認（模擬サーバーでのみ確認）、systemd 等の設定の実地確認、LLM 常時稼働の日次予算、実ブローカー用の復元（照合）、観測者の累積統計の永続化 |
| T8 | 閾値の実測 | スリッページ閾値(75bps/2件)などはペーパー（模擬約定）では実測できない |

## 3. Paper → Live の基準（たたき台・要判断）

**注意**: ペーパー成績が良いこと、特に短期間の成績は、実運用で利益が出る根拠にならない。基準は
「儲かるか」ではなく「安全装置が実際に働き、想定外が起きていないか」を主軸にする案とした。

| 区分 | 案（たたき台の数値） | あなたの判断 |
|---|---|---|
| 期間 | 連続 **60 営業日**以上のペーパー稼働（実LLM・実データ） | 期間は？ |
| 不変条件 | 期間中の INV 違反 0、未解決の照合不一致 0 | |
| 照合 | 毎セッション照合が全日成功。期間中の `HALT_NEW_ENTRIES` は原因が全て説明できる | |
| 監査 | 全注文が Audit を通過済み、監査不能による取りこぼし理由が記録済み | |
| 約定品質 | 実ブローカーの**ペーパー口座**（模擬ではなく）で十分な件数の約定を取り、想定価格との乖離分布を実測してからスリッページ閾値を確定 | 件数は？ |
| 損失 | 期間中の最大ドローダウンが許容範囲内（数値は運用者が決める。案: 資本の 10%） | 許容値は？ |
| 運用 | 緊急停止・LIVEゲート失効・切断復旧の**訓練**を各1回以上実施・記録 | |
| 費用 | LLM費用が期待エッジを食っていないこと（`QUANT_LLM_BUDGET_USD` 運用実績） | |
